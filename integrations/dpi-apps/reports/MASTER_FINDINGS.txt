################################################################################
PART 1 — THE ANSWER IN ONE PAGE
################################################################################
Something on this line reads the TLS ClientHello, matches the server NAME, and
drops the connection when the name matches a list. It does not need to decrypt
anything, and it never does.

For *.workers.dev specifically the name is read from the ClientHello, the
handshake is allowed to COMPLETE (Cloudflare's real certificate is delivered
intact), and then every client-to-server byte is discarded. You see a hang, not
an error, lasting about 15 seconds, after which Cloudflare gives up and closes.
There is no RST, no interception, and no certificate substitution.

Three consequences that decide everything else:

  1. The block is on the NAME, so it cannot be defeated from the client. Not by
     fragmenting the ClientHello (measured), not by renaming (measured), not by
     changing protocol, path, fingerprint, early data, or app.

  2. workers.dev hostnames are only ever ONE label deep, and the filter's
     matcher reaches four labels. So every possible workers.dev name is inside
     the blocked window, by construction. There is no workers.dev name that
     works from this line.

  3. Therefore the fix is not a setting. It is a different name — a hostname on
     a domain you control. Names with five or more labels are forwarded.

Alongside that sit three other mechanisms, all measured: DNS forgery for the
heavily censored sites, TCP reset for pages.dev and for every encrypted-resolver
hostname, and a working bypass for encrypted DNS that exists only because
addressing a resolver by IP removes the name from the wire.

PART 3 — WHAT THE FILTER IS, AND WHERE IT SITS
################################################################################
An SNI-based passive filter on this line, upstream of Cloudflare.

IT IS NOT:
  IP-based           The same anycast addresses (188.114.96/97/98) serve blocked
                     and allowed flows simultaneously, same machine, same
                     seconds: frames 27-67 blocked, frames 254-271 allowed.
  port-based         Port 80 to the blocked hostname returns HTTP 200 and the
                     Worker's own code executes.
  Host-header-based  SNI=workers.dev with Host=<blocked worker name> returned
                     Cloudflare's 403 in 0.30 s. The Host string is not the
                     trigger; the SNI is.
  content-based      The filter never sees content. The drop happens on the
                     first client record carrying application data, still opaque.
  a Cloudflare WAF   Cloudflare's own TCP state proves it never got the request.
  TLS interception    Cloudflare's genuine Let's Encrypt certificate is presented
                     and validates. So no decryption, no protocol visibility.

LOCATION
  Between this host and Cloudflare, on the MCI line. Not yet distinguishable
  between MCI's own filtering infrastructure and the CPE router on the local LAN;
  traceroute -T needs privileges this host does not have.

HARD PROOF IT IS NOT CLOUDFLARE — from the captured FIN:

  frame 196  t=18.194328827  188.114.97.3 -> 10.170.48.221
             [FIN, ACK] Seq=4889 Ack=1612 Win=131072

Cloudflare's own TCP accounting says: "I sent 4889 bytes and received only 1612."
1612 is exactly the ClientHello flight. The 287 bytes that followed (client
Finished plus the encrypted request, Seq 1612->1899) never arrived and were
never acknowledged. So Cloudflare never dispatched the request to the Worker,
never produced a response, and after its own ~15 s timeout closed by itself.
Our side shows the mirror image: ACK Seq=1899 Ack=4890, then duplicate ACKs
(frames 214, 219).

The ~15 second delay is therefore CLOUDFLARE'S TLS TIMEOUT, not a censorship
timer. This corrects an earlier reading that treated 15 s as a filter behaviour.

ROUTE
  13 hops to 188.114.97.3; TTLs 1-12 return EHOSTUNREACH, TTL 13 connects.
  SYN leaves with TTL 64, SYN-ACK returns with TTL 49, RTT 113 ms. The colo code
  on successful TLS requests is FRA (Frankfurt); the plaintext port-80 request
  came back GYD (Delhi). Consistent with a European path.
  "ping -M do -s 1472" succeeds, so the tested MTU-blackhole behaviour is ruled out.

EXIT-NODE LABELS ARE FICTION
  cf-ray ...-FRA for TLS, ...-GYD for the plaintext request. The subscription's
  "USA - New York", "Germany - Frankfurt", "Netherlands - Amsterdam" nodes are
  the same Frankfurt exit wearing different names. INFERRED from colo codes, not
  independently verified.

PART 6 — THE FIVE ENFORCEMENT MECHANISMS
################################################################################
The filter is not one mechanism. Five distinct responses were observed. The
differences matter for detection and for writing client rules.

MECHANISM 1 — DNS FORGERY
  Symptom   forged A and AAAA; no answer for NS/MX/TXT; identical answer no
            matter which resolver is asked; identical for case-randomised names
  Applies   facebook.com, instagram.com, youtube.com, x.com, pages.dev, and
            every encrypted-resolver hostname
  Values    A    = 10.10.34.36                (dead sinkhole)
            AAAA = 2001:4188:2:600:10:10:34:36  (documentation prefix, so the
                                                  address can never be real)
  TTL       ~417-418 on forged answers, lower on legitimate ones
  0x20 case randomisation does NOT help.

MECHANISM 2 — SNI SILENT DROP
  Symptom   TLS handshake COMPLETES, genuine certificate delivered, then zero
            application bytes; peer hangs until it times out
  Applies   *.workers.dev, 2 to 4 labels
  Not       MITM, certificate substitution, or injected RST

MECHANISM 3 — SNI TCP RESET
  Symptom   TCP RST during the handshake; handshake never completes
  Applies   pages.dev (apex, www, and nonexistent names); every DoH resolver name
  Why this is the filter and not Cloudflare: a nonexistent *.workers.dev name
  gets a genuine TLS alert from Cloudflare, whereas a nonexistent *.pages.dev
  name gets a RST. Cloudflare refuses neither; the connection dies upstream.

MECHANISM 4 — LABEL-COUNT WINDOW
  Symptom   names with 5 or more labels are forwarded untouched
  Scope     any hostname, not just workers.dev
  Note      this is a parsing limitation of the matcher, not a smarter filter.
            It is NOT a usable evasion for workers.dev, because Cloudflare
            serves no such name — the name is forwarded and then rejected.

MECHANISM 5 — PORT/ADDRESS SCOPING (observed, not fully characterised)
  1.1.1.1 and 1.0.0.1 time out even addressed by IP, while Cloudflare's CDN
  addresses connect fine. 8.8.8.8 and 9.9.9.9 refuse plain HTTP/80 connections
  while 1.1.1.1 answers 301 and doh.pub answers 403. So port and address
  behaviour varies per service and was not mapped exhaustively.

WHY FRAGMENTATION CANNOT HELP
The "tls fragment" file (/home/user fragment, a truncated JSON
paste fragment from the same panel) routes TLS through a "tcp-fragment-tls"
outbound whose streamSettings.finalmask splits the ClientHello (packets
"tlshello", then 114+1 byte fragments, maxSplit 11). Fragmentation only ever
helps against a filter that inspects the FIRST contiguous segment. This filter
reassembles first. Directly measured with ssl.MemoryBIO:

    SNI = <blocked worker name>
      single   (one write)               -> no response, 12 s timeout
      fragment (2 writes, 150 ms apart)  -> no response, 12 s timeout
      delay    (2 writes, 600 ms apart)  -> no response, 12 s timeout
    SNI = workers.dev      single 0.2 s / fragment 0.4 s / delay 0.8 s  -> fine
    SNI = cloudflare.com   single 0.2 s / fragment 0.4 s / delay 0.8 s  -> fine

So splitting the ClientHello changes nothing, and splitting a connection whose
SNI is blocked cannot hide that SNI. Finalmask buys nothing and costs throughput.

WITHDRAWN 3 — "the ~15 second delay is the filter's behaviour"
  It is Cloudflare's own TLS handshake timeout. Its FIN carries Ack=1612, proving

WITHDRAWN 4 — MY OWN SNI TESTER WAS WRONG FOR SEVERAL HOURS
  sni_variants.py, sni_variants2.py and sni_variants3.py all reported the CONTROL

  a false "0 bytes". Proof the control is reachable: 946 bytes of application
  data arrive in 0.25 s. sni_variants4.py decrypts through SSLObject.read() and
  is the ONLY tester whose output is citable. Every conclusion that rested on
  the earlier three files is void.

PART 10 — THE VENDOR QUESTION, STATED HONESTLY
################################################################################
NO vendor, model, or management interface has been identified. There is no
evidence for Huawei, ZTE, or any other appliance, and none for any throughput
figure.

WHAT IS KNOWN ABOUT THE INFRASTRUCTURE
  - The gateway at 10.170.48.246 exposes TCP/53 among scanned administration and
    DPI sinkhole ports, and nothing else identified. Router identity unknown.
  - The gateway MAC 36:a4:df:c6:e3:f6 is randomised, so no vendor OUI applies.
  - The sinkhole addresses 10.10.34.34, .35 and .36 answer nothing: no TCP or
    UDP service, no ICMP, no useful fingerprint. The gateway does not answer
    either.
  - The forged AAAA prefix 2001:4188:2:600:: is a documentation range, chosen
    for plausibility, not assigned to any operator.

WHAT IS INFERRED, NOT MEASURED
  - That the filtering sits on MCI's network rather than the local CPE, from the
    route and the fact that the drop is upstream of Cloudflare. Not proven.

CONCLUSION: the equipment has not been identified and probably cannot be from
the client side. An SNI string match and a silent flow drop are behaviour, not
a signature of any particular vendor.
