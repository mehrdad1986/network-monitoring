1. WHAT BLOCKS IT
================================================================================
An SNI-based, stateful, passive filter that classifies the flow from the SNI
string in the TLS ClientHello and then silently blackholes it.

It is NOT:
  - IP-based          same edge IP 188.114.96/97/98/99 serves both blocked and
                      allowed flows simultaneously (frames 27-67 blocked,
                      frames 254-271 allowed, same seconds, same machine)
  - port-based        port 80 to the same hostname works (200 OK, Worker code ran)
  - Host-header-based SNI=workers.dev + Host=jade-garden... -> Cloudflare answered
                      HTTP 403 in 0.30 s. The Host string is not the trigger.
  - content-based     the filter never sees content; the drop happens on the
                      first TLS record carrying application data, still opaque
  - a Cloudflare/WAF  Cloudflare's own stack proves it never received the request

Rule set — CORRECTED 2026-10-02 after a new control experiment.
An earlier version of this file claimed *.cloudflare.net and *.pages.dev are also
filtered. THAT CLAIM WAS WRONG and is withdrawn: those names also go silent when
forced onto a workers.dev edge IP, but that silence is Cloudflare's own edge
behaviour for a name it does not serve, not censorship. Control:

  go.dev          real IP 216.239.34.21   -> HTTP 200  (DPI does NOT block .dev)
  rust-lang.org   real IP 185.199.111.153 -> HTTP 200  (DPI does NOT block it)
  both of the above forced onto 188.114.97.3 -> silent (Cloudflare edge, not DPI)

What is actually established as filtered on AS197207:
  *.workers.dev  BLOCKED. Real host, "a.b.workers.dev", and names that do not
                 exist at all. Proven to be censorship and not Cloudflare by
                 three independent facts: (1) the same host answers HTTP 200
                 over plaintext port 80 from this machine, (2) the Cloudflare
                 edge completes TLS with a valid certificate and sends 4889 B of
                 its own flight, (3) Cloudflare's closing FIN carries Ack=1612,
                 proving it received the ClientHello but never the request.
  workers.dev apex  ALLOWED (301 from Cloudflare)
  cloudflare.com    ALLOWED (301 from Cloudflare, on the same edge IP)
  .dev as a TLD     ALLOWED (go.dev returns 200)
  Cloudflare as a vendor, and Cloudflare edge IPs, are NOT the trigger.

2. WHERE
================================================================================
Between 10.170.48.221 and 188.114.97.3 — upstream of Cloudflare, on this line.

Hard proof it is NOT Cloudflare, from the captured FIN:

  frame 196  t=18.194328827  188.114.97.3 -> 10.170.48.221
             [FIN, ACK] Seq=4889 Ack=1612 Win=131072

Cloudflare's own TCP state says: "I have sent 4889 bytes and I have received
only 1612 bytes." 1612 is exactly the length of the ClientHello flight. The 287
bytes that followed (client Finished + encrypted HTTP GET, Seq 1612->1899) were
never received by Cloudflare and were never acknowledged. Cloudflare therefore
never dispatched the request to the Worker, never produced a response, and after
~15 s of an incomplete handshake it closed the connection by itself.

Our own ACK at frame 197 also shows the same thing:
  frame 197  10.170.48.221 -> 188.114.97.3  [ACK] Seq=1899 Ack=4890
             + [TCP Dup ACK] SLE=4889 SRE=4890   (frames 214, 219)

So the drop is on the client-to-server direction, upstream of Cloudflare.
Not yet distinguishable: MCI's own filtering infrastructure vs. the CPE router
on the local LAN. That requires either root (traceroute -T needs privileges:
"socket: Operation not permitted") or a second device on a second network.

Hop count is consistent with a European path: our SYN leaves with TTL 64, the
SYN,ACK returns with TTL 49, RTT 113 ms, and the Cloudflare colo header on a
successful request is FRA.

6. ONE AMBIGUITY, STATED PLAINLY
================================================================================
  SNI-less ClientHello (openssl -noservername) to the blocked IP also produced
  silence. Two explanations fit and I did NOT separate them:
    (a) the filter also treats a missing SNI as suspicious, or
    (b) Cloudflare's edge simply does not answer HTTPS without SNI.
  Do not quote this as evidence either way.


================================================================================
7. WHAT THIS MEANS FOR THE FIX
================================================================================
  1. The filter reads the SNI. Anything that puts the real name in the SNI is
     exposed. There is no TLS-level workaround measured to work here.
  2. Port 80 to the same hostname was NOT filtered and the Worker executed
     (200 on /healthz, 404 from its own code on the upgrade). Plaintext ws://
     therefore appears to work from this line — untested end-to-end with a real
     VLESS client, and it removes TLS entirely, so it is a diagnostic, not a plan.
  3. The durable fix is a domain you own on Cloudflare: the SNI becomes an
     ordinary domain, the pattern rule above does not match it, and the traffic
     looks like ordinary HTTPS to a web server.
  4. After deploying, re-run exactly these tests before distributing nodes:
       - same tests against the new host must return bytes
       - a NON-EXISTENT subdomain of your zone forced onto the same IP with
         curl --resolve must ALSO return bytes. If the fake name is blackholed
         too, your whole domain is filtered.
