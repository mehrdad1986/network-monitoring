PART 4 — YOUR QUESTION: DOES THE DPI FIND AND BLOCK VLESS?
================================================================================
In your current setup: NO. Measured, not assumed.

  * curl verified Cloudflare's certificate. No TLS interception, therefore no
    decryption, therefore no visibility of the VLESS header, the UUID, the
    destination, or the WebSocket frames.
  * The tunnel bytes never reached Cloudflare (Ack=1612). The filter acted on
    the ClientHello alone.

Two different situations where protocol-level blocking WOULD apply, neither of
which is yours:

  a) You run plaintext VLESS (no TLS, ws:// / raw TCP). Then the header is
     cleartext and rigid: byte 0 = 0x00 (version), bytes 1-16 = the UUID at a
     fixed offset, then command/port/address type, and the destination host is
     readable. Passive detection is easy. Do not do this.
  b) The filter terminates TLS with a certificate your client accepts. Not the
     case here, and not something Iranian operators do to general traffic.

So: the DPI does not need to understand VLESS. Blocking the entry name is
cheaper and more robust than fingerprinting a tunnel.

PART 5 — PRACTICAL PLAN, ONE APP ONLY
================================================================================

Q: Does TLS ClientHello fragmentation need a second program?
A: No. Both apps you named have it built in, because both drive Xray-core or
   sing-box, which implement fragmentation natively. No sidecar, no extra VPN.

  v2rayNG
    Newer versions: open the server -> Edit -> "Fragment" field ->
      Fragment = tls-clienthello, Length = 100-200, Interval = 10-20
    Older versions: Settings menu -> "Fragment" / "Enable Fragment"
    Hiddify
    Settings -> Fragment / "TLS Fragmentation" -> enable, set length + interval
    (Hiddify runs sing-box by default; the equivalent sing-box knob is the
     fragment option in the outbound TLS settings)
  Exact menu wording changes between versions; if you cannot find it, the JSON
  in the outbound is roughly:
      "fragment": { "packets": "tls-clienthello", "length": "100-200",
                    "interval": "10-20" }

  BUT: I measured this and it does NOT work on your line. Set it if you like,
  it costs nothing, but do not expect it to be the fix. It only helps against
  filters that match a contiguous ClientHello; this one reassembles first.

WHAT ACTUALLY MATTERS, in order:

  1. GET A DOMAIN AND STOP USING workers.dev.  (the only measured fix)
       - buy any cheap domain, add it to your Cloudflare account
       - DNS: *  CNAME  example.com   (proxied / orange cloud)
       - wrangler.toml:
             routes = [{ pattern = "*.example.com/*", zone_name = "example.com" }]
       - in the Worker, set SUB_BASE_DOMAIN = example.com
         (worker(3).js then emits de01.example.com ... no07.example.com)
       - in v2rayNG/Hiddify the server address, SNI and Host all become
         de01.example.com — a name that is not on the list

  2. In v2rayNG/Hiddify, remove the raw Cloudflare IPs from the server address.
       server = your subdomain, not 104.19.x / 188.114.x. Those IPs pin you to
       one edge and buy nothing.

  3. Set EARLY_DATA=0 on the Worker. It is not the fix, but it is free, it
       removes a 200-2700 character base64 blob from the first request, and it
       costs one extra round trip.

  4. Optional hardening, cheap: serve a real page at "/" instead of 404, set
       HEALTHZ=0, and use a generic WebSocket path. These do not defeat the
       name filter; they reduce the chance of your hostname being reported.

VERIFY IN ONE MINUTE, from inside the app or a browser on the Iranian line:
       curl -m 12 -o /dev/null -w '%{http_code}\n' https://de01.example.com/
     200 or 301 or 404-from-your-Worker = reachable.
     000 = still filtered.

VERIFY THE DOMAIN IS NOT ON A LIST (this is the important second test):
       curl -m 12 -o /dev/null -w '%{http_code}\n' \
        --resolve zzzfake9182.example.com:443:$(getent ahostsv4 example.com | awk '{print $1}' | head -1) \
        https://zzzfake9182.example.com/
     A fast HTTP answer (404/530/301) = the zone is clean.
     000 = your whole domain is filtered, rotate to another one.

IF YOU REFUSE TO BUY A DOMAIN:
  nothing on Cloudflare Workers will work. The SNI is always present in TLS and
  every Workers hostname is <something>.workers.dev. The only SNI-free option is
  no TLS at all, which exposes the VLESS header in cleartext — strictly worse.
